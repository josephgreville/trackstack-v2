# Testing TrackStack

## Requirements

- Node.js and npm for the workspace packages.
- PostgreSQL for API and database tests.
- A dedicated test database whose name ends in `_test`. Never point test commands
  at a development or production database.

Configure `TEST_DATABASE_URL` in the root `.env`, for example:

```text
TEST_DATABASE_URL=postgres://trackstack:your-local-password@localhost:5432/trackstack_test
```

The test database setup command verifies the `_test` suffix, applies migrations,
and truncates test tables. The server test setup repeats the database-name
guard and clears records before every test. Server tests run in one worker
because they share this database. Keep test credentials local.

Start or provision PostgreSQL separately, then run:

```sh
npm run db:test:setup
```

## Test commands

```sh
npm test                    # Prepare the isolated test database and run client + server suites
npm run test:client         # Frontend component, page, and API-client tests (no database required)
npm run test:server         # Prepare the isolated test database and run API + database tests
npm run test:database       # Run only relational schema and constraint tests
npm run test:coverage       # Prepare the database, run all suites, and generate coverage
```

Coverage output is generated by Vitest in `coverage/`. The suite covers observable page behavior, authentication and registration,
collection CRUD, album search and selection, validation and error states,
request/response contracts, ownership boundaries, database constraints,
transaction rollback, and mocked catalogue responses. External iTunes calls
are mocked in server tests. The album-details page now lets a signed-in user
choose a collection and add the displayed album.

## Browser end-to-end testing

Playwright is not currently installed or configured in this repository. The
application also has no automated browser-test server/database lifecycle, so
there is no `test:e2e` command yet. Browser journeys should be added once a
dedicated Playwright setup can start the app against isolated test data; do not
run browser tests against personal or production accounts.

## Checklist audit boundaries

The automated suite verifies application behavior at component, API, and
database levels, but it does not certify every visual or deployment-specific
checklist item. In particular:

- Responsive overflow, touch-target sizing, color contrast, reduced motion,
  zoom behavior, and keyboard focus need browser/assistive-technology checks.
- Collection album sorting is available through the API, but the collection
  detail page does not currently expose sort controls.
- Rate limiting is configured for production but intentionally skipped in test
  mode, so thresholds are not exercised by the automated suite.
- iTunes outages are simulated; production network, database outages, and
  deployment cookie/CORS settings require environment-specific smoke tests.
- No complete browser journey is automated across registration, session,
  collection creation, album addition, refresh, and sign-out.
