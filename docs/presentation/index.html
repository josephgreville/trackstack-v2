The brief

People who share an interest,
sharing their things

  • Every user → many collections
  • Every collection → many records
  • Records come from a real catalogue — iTunes
  • Each copy has format, condition, price

Why records?

The data is genuinely relational: one record can sit in many collections, and every copy is its own thing with its own condition and price. The modelling problem is the interesting part — not the CRUD.

TrackStack · Final Project06
Architecture

Why these choices

PostgreSQLThe data is relational — I wanted the database to enforce it: foreign keys, CHECK constraints on format and condition, unique indexes on lower(email). A document store means hand-rolling integrity.
No ORMExplicit SQL, so I can explain every query and every index. That was the part I was asked to understand.
Sessions, not JWTThe cookie holds only a signed id — an XSS bug can't read it, and I can revoke a session server-side.
Own APIOur Express API is the source of truth for users, collections, copies. iTunes only supplies catalogue metadata.
MonorepoClient and API in one repo, one install, one dev command, one deploy.

TrackStack · Final Project08
Security

Keys, sessions, and other people's data

API keys

There are none.
The iTunes Search API needs no key, and every call is made from the server — so no key can reach the browser bundle. The only secrets are DATABASE_URL and SESSION_SECRET, both in environment variables, and .env is git-ignored.

Sessions

Server-side, stored in Postgres, signed id in an httpOnly cookie, SameSite, Secure in production, revocable server-side. bcrypt for passwords. Rate limits on login.

Ownership

Every personal query is scoped by user_id from the session inside the service, not the route. Another user's collection returns 404 — it never confirms the thing exists. There are tests for exactly this.

A thumb reaches the bottom of a phone, not the top. So the tabs move to a floating bottom dock — with safe-area padding.

Sticker-book aesthetic: 2px outlines, solid offset shadows, no blur, pill buttons, spring motion. The palette lives in one token file — a colour change is one edit. Every animation respects prefers-reduced-motion.

Why one service

Same origin → the cookie stays SameSite=Lax, no CORS, one URL for the demo. Migrations are numbered SQL files and run at container start; they're idempotent, so every redeploy is safe.

Also documented

The split option — Netlify for the client, Railway for the API — plus a local-only docker compose path. The image is portable to any container host.

TrackStack · Final Project12
Reflection

What went well, what didn't

Worked

• Schema decided first — every feature followed from it
• Small commits, one feature at a time
• AI wrote the code; I chose the boundaries
• Layers kept generated code coherent

Didn't

• Scope — the 2.0 features took twice as long as 1.0
• First pass looked like every other AI app
• Free hosting sleeps; a demo-day risk
• No backups on a free database

Learnt

• A "collection" is a join table plus copy details, not a list of ids
• Testing the real database caught what mocks hid
• Scope control is a technical skill
